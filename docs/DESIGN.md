## 2. 项目定位

- 类型：原作结局之后的同人续篇角色卡，承载于 SillyTavern 的重型同层前端。
- 玩家：诺雅。模型描写环境、莉莉希雅及其他人物，诺雅的决定留给玩家。
- 核心价值：让原作篇幅之外的共同生活与月光都市瑟雷妮亚真正活起来，而非复刻原作的三十日养成限制。
- 关系：两人明确处于恋人关系，这是本作采用的同人续篇选择；重心是互相依偎、共同生活，不是持续腻歪的热恋表现。
- 莉莉希雅有自己的愿望、邀请与烦恼，可以主动推进生活；她的主动性不替代玩家选择。
- 主菜：宅邸日常与自然外出。城市通过氛围、习俗、人与人之间的往来呈现，首版不要求街道名录或固定原创人物群。
- 时间：随着实际行动自然推进，不按每条消息固定扣时，也不预设新一轮三十日期限。

### 前端适配判断

推荐同层前端，但须通过原型与真实酒馆验收。理由是用户明确需要由同层前端托管整个聊天界面，减轻长消息阅读与反复翻楼层的负担，而不是仅增加一块装饰状态栏。聊天生成和存储仍由酒馆负责。

若实际宿主接入或长聊天性能未达到验收标准，先停在失败阶段收集证据。普通酒馆聊天加轻量状态栏可作为重新讨论的缩减方案，仅为候选，不自动替换已确认形态。

## 4. 首次进入与核心循环

### 4.1 起点

- 时间：续篇第 1 日·上午。此编号是续篇计时，不断言为原作第 31 日。
- 地点：宅邸起居室。
- 莉莉希雅：居家便服、神态放松、无明显不适；具体图像与文字描述须相符。
- 事件入口：莉莉希雅提出寻找两人共用香气的邀请。
- 玩家可接受、推迟、改变计划；不强制采购，不强制获得新颜色或属性增长。

### 4.2 主循环

阅读场景与人物状态 → 以诺雅身份输入行动或回应 → 酒馆生成正文及状态变化清单 → 检查并保存这一回复的有效状态 → 界面更新 → 玩家继续或回看历史。

外出路径可包含讨论香气、感受城市生活、形成共同体验、回到宅邸。它是可玩主路径，不是锁定的任务步骤；留在家中也应自然继续。

## 5. 界面与视觉合同

### 5.1 阅读与输入

- NVL：场景图位于正文背后，使用稳定的遮罩和对比度保障阅读。
- 一条完整回复作为一个阅读单元；流式接收时允许逐步显示已到达的正文，完成后不再拆成点击推进的句子或片段。不强制打字机动效。
- 长回复在阅读区内滚动；提供前后轮阅读、独立历史入口和返回最新。
- 人物栏与正文分离，不用大幅立绘压缩阅读空间。
- 前端负责呈现和输入；真实聊天记录、生成与保存沿用酒馆。
- 草稿、阅读位置等界面状态与游戏状态分开。回看历史显示该节点正文及对应人物状态，不改写当前进度。
- 桌面与手机同等优先。手机采用重新排布，不是缩小桌面；检查软键盘、正文滚动、人物栏及输入区相互影响。

### 5.2 颜色与动效

- 黑白是主体；首版场景和人物保持灰阶，色彩用于部分 UI、文字强调和装饰。
- 初始已获得红、绿、蓝、橙四种颜色。续篇不把既有颜色清零；新颜色来自有意义的经历，不设置强制收集清单。
- UI 分类用色：技能橙色、教养蓝色、人格绿色、本能红色。这是界面编码，不自动宣称为原作魔法规律。
- 渐进着色须跟随已保存的有效颜色状态，重复获得同色不重复计入。后续逐渐丰富色彩，但保留正文可读性。
- 动效只解释场景、面板或有效状态的变化，不用持续动画抢夺注意力。减少动效、键盘操作、可见焦点与文字状态标记列入基础检查。
- 每名展示角色均有小头像。首版首先保障诺雅与莉莉希雅；其他角色不预建空数据或空素材目录。

### 6.1 成长与消耗

八项长期数值是扫除、料理、洗涤、礼仪、知识、魅力、亲爱、感度。

| 经历类型 | 长期数值变化 |
| --- | --- |
| 缺少对应有效经历 | 0 |
| 有效日常练习或体验 | +1～3 |
| 学会新方法、理解新事物等明确进展 | +4～8 |
| 有充分叙事依据的显著突破 | +9～15 |

- 以一次有意义的经历为结算对象，不以消息条数计奖。换句说法、拆成多条消息、刷新或重生成不重复奖励。
- 只变更直接相关字段；日常练习也能积累，而非只奖励里程碑。
- 疲劳、一次失误不自动扣长期技能；普通分歧不自动扣亲爱。
- 体力、魔力、欲求按实际事件增减：轻微 1～5、明显 6～15、大幅 16～30；大幅变化需明确依据，最终保持 0～100。
- 无每消息自动消耗、无被动欲求增长、无固定体力与魔力兑换公式。欲求高不自动行动，也不自动增加感度。
- 数值主要辅助叙事，首版不以它们建立普遍的硬行动门槛。

## 7. 状态权威与结算合同

### 7.1 一条回复，两部分输出

同一次生成给出故事正文和有明确边界的结构化变化清单。清单只列本轮变化及简短故事事实依据；没有变化时明确为空，区别于缺失输出。正常阅读隐藏清单，但保留检查与修复入口。

模型提出变化，脚本执行确定性计算并保存，前端只消费结果。脚本检查字段、格式、范围和重复结算；剧情依据是否充分主要依赖模型规则与试玩检查，不宣称脚本能自动裁定全部语义。

确切机器字段名、清单边界与格式在 P0 定义最小合同；不预设完整框架，不加载第二个更新模型。

### 7.2 唯一状态源

- 复用酒馆助手原生消息变量，把完整状态快照绑定到对应回复分支。
- 只有卡片自身的结算逻辑写入本卡状态；修改时保留同一消息变量中其他脚本的数据。
- 生成前提供当前有效状态和规则，模型看到的状态与前端采用的状态一致。
- 消息标识、分支、内容修订与结算标记由脚本管理，不让模型自报身份。
- 位置编号不是永久身份：删消息或移动消息后须重新核对上下文；切换聊天后丢弃原聊天迟到的处理结果。
- 起始状态来自明确的新聊天基线。既有聊天缺少有效状态时进入待同步，不用初始化值覆盖历史。

### 7.3 整轮提交、分支对应

- 流式到达时仅暂存；完整、有效且属于当前所选回复的结果才进入结算。
- 整份变化清单检查通过后一起应用，避免半轮结算。出现未知字段或非法结构时报告问题，不静默丢字段后假装成功。
- 重生成从该轮开始前的有效状态计算；切换回复使用相应分支结果。重复事件、刷新或重新打开不重复加减。
- 历史编辑、删除或分支变化会影响后续状态依据：对受影响的后续结果标记失效，核对或修复后再推进，不让旧快照继续冒充有效状态。
- 回看历史只改变视图。界面明确区分历史节点与当前可继续的节点。
- 内存写入成功与磁盘保存完成分开判断；真实刷新和重开验收必做。

### 7.4 异常路线 A：暂停推进

1. 清单缺失、检查失败或当前状态依据失效时，本轮变化暂不生效。
2. 保留正文、输入草稿与历史阅读；人物栏显示上一份有效状态及“状态待同步”。
3. 暂停发送下一轮，并说明具体问题；支持修正当前回复的状态清单，或由玩家主动重生成当前回复。
4. 修复后从原本的本轮起点重算，只结算一次；重新校验修订关系后才恢复发送。
5. 保留草稿，由玩家自行发送；不在后台自动重生成或额外调用模型。
6. 修复入口是必要功能，但首版不因此建立通用状态管理后台。
