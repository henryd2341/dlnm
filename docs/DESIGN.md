## 2. 项目定位

- 类型：原作结局之后的同人续篇角色卡，承载于 SillyTavern 的重型同层前端。
- 玩家：诺雅。模型描写环境、莉莉希雅及其他人物，诺雅的决定留给玩家。
- 核心价值：让原作篇幅之外的共同生活与月光都市瑟雷妮亚真正活起来，而非复刻原作的三十日养成限制。
- 关系：两人明确处于恋人关系，这是本作采用的同人续篇选择；重心是互相依偎、共同生活，不是持续腻歪的热恋表现。
- 莉莉希雅有自己的愿望、邀请与烦恼，可以主动推进生活；她的主动性不替代玩家选择。
- 主菜：宅邸日常与自然外出。城市通过氛围、习俗、人与人之间的往来呈现，首版不要求街道名录或固定原创人物群。
- 时间：随着实际行动自然推进，不按每条消息固定扣时，也不预设新一轮三十日期限。

### 前端适配判断

推荐同层前端，但须通过原型与真实酒馆验收。理由是用户明确需要由同层前端托管整个聊天界面，减轻长消息阅读与反复翻楼层的负担，而不是仅增加一块装饰状态栏。聊天生成和存储仍由酒馆负责。

若实际宿主接入或长聊天性能未达到验收标准，先停在失败阶段收集证据。普通酒馆聊天加轻量状态栏可作为重新讨论的缩减方案，仅为候选，不自动替换已确认形态。

## 4. 首次进入与核心循环

### 4.1 起点

- 时间：续篇第 1 日·上午。此编号是续篇计时，不断言为原作第 31 日。
- 地点：宅邸起居室。
- 莉莉希雅：居家便服、神态放松、无明显不适；具体图像与文字描述须相符。
- 事件入口：莉莉希雅提出寻找两人共用香气的邀请。
- 玩家可接受、推迟、改变计划；不强制采购，不强制获得新颜色或属性增长。

### 4.2 主循环

阅读场景与人物状态 → 以诺雅身份输入行动或回应 → 酒馆按本卡已绑定的世界书与规则生成正文及 MVU 更新 → MVU Zod 更新有效状态 → 前端显示对应正文与状态 → 玩家继续或回看历史。

酒馆生成属于复用能力，不设“能否得到一次回应”的独立测试阶段。项目验收针对本卡接入：世界书上下文、正则呈现、MVU Zod 状态和最终前端是否一致；真实生成只在这条完整链路有验证价值时使用。

外出路径可包含讨论香气、感受城市生活、形成共同体验、回到宅邸。它是可玩主路径，不是锁定的任务步骤；留在家中也应自然继续。

## 5. 界面与视觉合同

前端技术栈固定为 **Vue 3 + TypeScript + Vite**（2026-09-23 用户补充）：Vue 3 负责界面组件，TypeScript 负责维护源码，Vite 负责开发与构建。构建产物仍接入酒馆同层前端，不变成独立网站或第二套聊天系统；游戏状态仍以 MVU Zod 为唯一来源。

本地开发交付采用一条最小路径：`delivery.config.mjs` 集中维护开发源 `http://127.0.0.1:5173`、资源基址 `http://127.0.0.1:5173/` 及允许的本机酒馆来源；`npm run dev` 仅用 Vite 托管已经构建到 `dist` 的文件，没有源码热更新，源码变化后须重新构建并导入新卡包，旧卡仍引用其原版本。`npm run build` 负责两次 Vite 构建后打包角色卡；`npm run pack` 只固化已有构建产物并组装卡，不串联测试。获得远程仓库后再把固定版本资源地址换成远程地址，本轮不提前引入 watch、同步器或 CI。

内容与装配分责但不新增框架：`src/card-content.ts` 承接世界书、创作文本和卡元数据，`src/card.ts` 只保留卡片组装及世界书、正则、脚本绑定；保留现有 MVU 接入与 Vue 入口，不搬模板覆盖项目文件。构建输出使用不可覆盖的 `dist/p<阶段>-<内容hash>/schema.js`、`state.js`、`state.css`、`state.html`；角色卡 JSON 在现有酒馆助手消息 iframe 中按固定版本 Vite 资源 URL 执行，不再套一层跨源 iframe，也不改变已固定的 MVU 上游提交。

### 5.1 阅读与输入

- NVL：场景图位于正文背后，使用稳定的遮罩和对比度保障阅读。
- 2026-09-24 最新手验纠正：全屏明确使用浏览器 **Fullscreen API**，不是网页覆盖层或填满 chat。默认提供“浏览器全屏阅读”入口，由点击同步调用 `requestFullscreen()`；首次加载不自动进入，以保留浏览器要求的用户手势。保留可切换的“面板模式”作为非全屏选项；返回酒馆和 Escape 退出本卡全屏。
- 全屏目标为宿主 documentElement，内容通过 Vue Teleport 放到顶层 dialog 内的隔离样式容器，逻辑继续由原消息 iframe 驱动；不移动 iframe、不修改原聊天布局。消息 iframe 换代复用已进入的浏览器全屏，全页刷新后重新点击。监听 `fullscreenchange` 收回阅读层；模式选择按聊天保存，不退出其他界面取得的全屏。
- 同份 Vite 编译 CSS 以 `style#dlnm-nvl-style` 封装在卡片 HTML 中；面板原位使用，全屏复制准确标记内容到 ShadowRoot。禁止选择 iframe 第一张样式表代替本卡样式；Helper 会先注入自己的样式，选到它会造成 NVL 样式丢失。
- 一条完整回复作为一个阅读单元；流式接收时允许逐步显示已到达的正文，完成后不再拆成点击推进的句子或片段。不强制打字机动效。
- 长回复在阅读区内滚动；提供前后轮阅读、独立历史入口和返回最新。
- 人物栏与正文分离，不用大幅立绘压缩阅读空间。
- 前端负责呈现和输入；真实聊天记录、生成与保存沿用酒馆。
- 草稿、阅读位置等界面状态与游戏状态分开。回看历史显示该节点正文及对应人物状态，不改写当前进度。
- 桌面与手机同等优先。手机采用重新排布，不是缩小桌面；检查软键盘、正文滚动、人物栏及输入区相互影响。

### 5.2 颜色与动效

- 黑白是主体；首版场景和人物保持灰阶，色彩用于部分 UI、文字强调和装饰。
- 初始已获得红、绿、蓝、橙四种颜色。续篇不把既有颜色清零；新颜色来自有意义的经历，不设置强制收集清单。
- UI 分类用色：技能橙色、教养蓝色、人格绿色、本能红色。这是界面编码，不自动宣称为原作魔法规律。
- 渐进着色须跟随已保存的有效颜色状态，重复获得同色不重复计入。后续逐渐丰富色彩，但保留正文可读性。
- 动效只解释场景、面板或有效状态的变化，不用持续动画抢夺注意力。减少动效、键盘操作、可见焦点与文字状态标记列入基础检查。
- 每名展示角色均有小头像。首版首先保障诺雅与莉莉希雅；其他角色不预建空数据或空素材目录。

### 5.3 最小素材与复用

首版至少需要两名主角的小头像，以及可用于宅邸、城市阅读场景的灰阶背景。实际数量由最小场景需求确定，不提前建图库。

| 来源 | 复用判定 | 边界 |
| --- | --- | --- |
| 原作翻译对照与书籍设定 | 原作资料依据 | 核对原文和译文，不把译文中的错配当作权威 |
| 用户提供的两张游戏截图 | 仅视觉参考 | 参考黑白底图与彩色分类；不抄用截图里的养成数值作为初始值 |
| 官方网站 | 仅风格参考 | 参考月光、花饰、字体层级等意象；不自动导入图片或代码 |
| 已安装的酒馆与酒馆助手能力 | 计划复用 | 源码级证据与运行验收分开；实施前复查版本 |
| 尚未提供的旧卡组件 | 尚无复用结论 | 不宣称已有稳定源码或可移植组件 |

本地拥有游戏文件不等于已取得素材再分发许可。参考、个人测试与打包分享分别登记；首版交付前解决实际采用素材的来源与使用边界。

### 6.1 成长与消耗

八项长期数值是扫除、料理、洗涤、礼仪、知识、魅力、亲爱、感度。

| 经历类型 | 长期数值变化 |
| --- | --- |
| 缺少对应有效经历 | 0 |
| 有效日常练习或体验 | +1～3 |
| 学会新方法、理解新事物等明确进展 | +4～8 |
| 有充分叙事依据的显著突破 | +9～15 |

- 以一次有意义的经历为结算对象，不以消息条数计奖。换句说法、拆成多条消息、刷新或重生成不重复奖励。
- 只变更直接相关字段；日常练习也能积累，而非只奖励里程碑。
- 疲劳、一次失误不自动扣长期技能；普通分歧不自动扣亲爱。
- 体力、魔力、欲求按实际事件增减：轻微 1～5、明显 6～15、大幅 16～30；大幅变化需明确依据，最终保持 0～100。
- 无每消息自动消耗、无被动欲求增长、无固定体力与魔力兑换公式。欲求高不自动行动，也不自动增加感度。
- 数值主要辅助叙事，首版不以它们建立普遍的硬行动门槛。

| 机器路径 | 类型与约束 | 初始值 | 读取与显示 |
| --- | --- | --- | --- |
| `world.day` | 正安全整数；变更后不小于该轮起点 | `1` | 模型与场景标题；续篇计日 |
| `world.period` | 清晨、上午、午后、傍晚、夜间、深夜之一 | `上午` | 模型与场景标题；没有按消息自动跳时段 |
| `world.location` | 1～80 字符的非空文本 | `宅邸起居室` | 模型与场景标题；不是地图节点 |
| `noa.colors` | 去重的非空颜色名称数组；单项 1～16 字符 | `["红","绿","蓝","橙"]` | 模型与诺雅颜色栏；不从截图推导额外颜色 |
| `lilixia.appearance` | 1～120 字符的非空文本 | `平日模样` | 模型与莉莉希雅人物栏；具体外形由原作/素材核对补足 |
| `lilixia.clothing` | 1～120 字符的非空文本 | `居家便服` | 模型与莉莉希雅人物栏 |
| `lilixia.expression` | 1～120 字符的非空文本 | `神态放松` | 模型与莉莉希雅人物栏；仅可观察表现 |
| `lilixia.condition` | 1～120 字符的非空文本 | `无明显不适` | 模型与莉莉希雅人物栏；不是隐藏心理读数 |

全部字段共享下列责任，不另建字段框架：

- **写入者：**MVU 的更新链与本卡 Zod Schema。模型仅提出变化；前端显示和用户主动修复均沿同一更新链，不再自建原生消息变量结算器。
- **读取者：**生成前的状态提示、当前/历史人物栏。两者读取同一有效快照；回看不改当前快照。
- **初始化：**通过与实际 MVU Zod 版本匹配的初始化条目及 Schema，使用本节默认值并对应开场分支。既有聊天缺记录、数据结构损坏或版本不认识时标记待同步，保留原数据。
- **更新：**一轮先校验全部变更，再从该轮起点计算整份新快照；有任一错误就保留上一有效快照。数值及文本不另存第二份可写 UI 状态。
- **清理：**切聊天/销毁时取消监听、临时提示注入和未完成处理，保留磁盘聊天；已删除消息随宿主删除，其下游须重核。首版没有历史迁移脚本或自动重置。
- **显示：**状态文本按文本渲染，不执行 HTML、宏、路径或代码。颜色名称不是 CSS；渲染器只用自己的固定配色映射，未知名称仍显示文本，不自动加载素材。

## 7. 状态权威与结算合同

### 7.1 一条回复，两部分输出

同一次生成给出故事正文和有明确边界的结构化变化清单。清单只列本轮变化及简短故事事实依据；没有变化时明确为空，区别于缺失输出。正常阅读隐藏清单，但保留检查与修复入口。

模型提出变化，MVU 更新链执行更新，本卡 Zod Schema 约束字段与范围，前端只消费有效结果。优先复用 MVU 已有的解析、存储和事件能力；项目仅补已证实的接入缺口。剧情依据是否充分仍依赖模型规则与试玩检查，不把结构校验当作语义裁判。
